# Логика проекта RUWORK

RUWORK — демо-маркетплейс фриланс-услуг. Сервер на FastAPI хранит все данные в SQLite (`ruwork.db`) и проверяет все действия с деньгами и аккаунтами. Браузер (`public/index.html`) только рисует страницы и обращается к API через `fetch`. В `localStorage` браузер хранит только удобства посетителя: тему, корзину и недавно просмотренные услуги.

## 1. Сервер (`app/main.py`)

1. При старте `init_db()` создаёт таблицы и, если каталог пуст, загружает услуги и продавцов из `app/seed.json`.
2. Маршруты `/api/...` — JSON API (документация: `/api/docs`). Неизвестный `/api/...` → `404`.
3. Любой другой путь: если такой файл есть в `public/`, он отдаётся, иначе отдаётся `index.html` (SPA-фолбэк). Выход за пределы `public/` через `../` невозможен.

## 2. Клиент: маршрутизация

При загрузке `boot()` запрашивает `/api/meta`, `/api/gigs`, `/api/state` и рисует экран. Навигация через хэш, `route()` перерисовывает `#app`:

| Хэш | Экран |
|---|---|
| `#/` | Главная: поиск с подсказками, категории, популярные услуги |
| `#/catalog` | Каталог с фильтрами |
| `#/gig/<id>` | Страница услуги: слева описание, тарифы с кнопками «В корзину» / «Купить сейчас» и отзывы; справа чат с продавцом и карточка продавца |
| `#/checkout` | Корзина и оплата |
| `#/dashboard[/<вкладка>]` | Кабинет (или вход/регистрация) с вкладками: `buy` «Покупки» (по умолчанию), «Продажи» (ведёт на `#/sales`), `gigs` «Объявления», `favs` «Избранное», `wallet` «Кошелёк», `profile` «Профиль» (в т. ч. «О себе») |
| `#/seller/<id>` | Публичный профиль продавца: имя, «О себе», дата регистрации, число выполненных и текущих заказов, значок «ТОП-продавец» (больше 150 выполненных), все объявления |
| `#/sales` | История продаж: заказы по своим объявлениям |
| `#/support` | Поддержка (кнопка внизу личного кабинета и ссылка в подвале): юзернейм бота копируется по нажатию, кнопка «Перейти в Telegram» открывает бота (`t.me/<бот>?start=support`). Без бота — контакт @ruwork001 |
| `#/order/<id>` | Страница заказа: данные, блок «Результат», подтверждение получения |

**Телефон или компьютер.** При каждой загрузке страницы скрипт определяет устройство (`PHONE`): телефон — если браузер сообщает, что он мобильный (`userAgentData.mobile` или User-Agent с iPhone/Android Mobile), либо экран сенсорный и его короткая сторона меньше 600px. На телефоне у `<html>` появляется класс `phone`: карточки услуг становятся компактными, по 2 в ряд (картинка, название, цена), а категории, подкатегории, цена и сортировка в каталоге открываются выпадающим окном по кнопке «Категории». На компьютере вид не меняется.

**Метка «ТОП».** Объявление получает метку «ТОП», когда у него 10 выполненных заказов (статус «Выполнен», `TOP_SALES` в `app/logic.py`). Ещё «ТОП» получают все объявления продавца, у которого на аккаунте больше 150 выполненных заказов по всем объявлениям (`TOP_SELLER_SALES`). Отменённые и незавершённые заказы не считаются, поэтому накрутить метку заказом с последующей отменой нельзя. Счётчик `sold` приходит вместе с объявлением. В каталоге при сортировке «По популярности» объявления с «ТОП» идут первыми.

**Тема оформления.** В профиле есть переключатель «Светлая / Тёмная». Выбор хранится в браузере (`localStorage`, ключ `ruwork-theme`) и применяется ещё до отрисовки страницы, без мигания. Светлая тема — класс `light` на `<html>`: светлые фоны, тёмный текст, приглушённые акценты. По умолчанию тёмная, она не изменилась.

Корзина хранится в памяти страницы и пропадает при перезагрузке, как и раньше.

## 3. База данных

| Таблица | Что хранит |
|---|---|
| `users` | id, имя, email, соль, хэш пароля, время последней активности, блокировка (время и причина) |
| `sessions` | токены входа (cookie `ruwork_sid`, HttpOnly, 30 дней) |
| `sellers` | описание и отзывы продавцов каталога |
| `gigs` | услуги: встроенные (`g-001…`) и объявления пользователей (`u-…`, с `owner_id`) |
| `orders` | заказы: номер, услуга, тариф, статус, сумма, способ оплаты, время, продавец и отметка о показанном ему уведомлении |
| `wallets` | баланс монет пользователя |
| `wallet_ops` | операции: пополнение, возврат на карту (`src` — пополнение, к которому он относится), вывод, оплата, возврат за заказ |
| `order_files` | файлы результата заказа: имя, тип, размер, сколько загружено (сами файлы — в `uploads/results/`) |
| `notifications` | уведомления колокольчика: кому, вид (`sale`, `result`, `done`, `cancel`, `msg`, `dispute`, `remind`, `wallet`), текст, ссылка, прочитано |
| `favorites` | избранное: пользователь — объявление |
| `platform_ops` | поступления на баланс платформы: комиссии с продаж и за вывод, удержания при отмене |
| `tg_support` | какое сообщение в чате поддержки от какого клиента (для ответа реплаем) |
| `chat_messages` | история чатов (по пользователю или по гостевой cookie `ruwork_vid`) |

## 4. Услуги и тарифы

Тарифы вычисляет `mk_tiers(base)` (`app/logic.py`) из базовой цены:

| Тариф | Цена | Срок | Правки |
|---|---|---|---|
| Стандарт | base × 1 | 5 дней | 3 |
| Стандарт+без очереди | base × 1,5 | 3 дня | 3, заказ берётся в работу первым |

Название тарифа сохраняется в заказе (`orders.tier_name`). Заказы, оформленные до смены тарифов, сохранили прежние названия «Эконом», «Стандарт» и «Бизнес».

Поиск и фильтры работают в браузере по загруженному каталогу: слова без окончаний, синонимы (`SYN`), совпадение в названии весит больше, чем в подкатегории.

## 5. Аккаунты (`app/auth.py`, `app/routes/account.py`)

- **Регистрация через Telegram** (когда настроен бот, `RUWORK_TG_TOKEN`; `/api/meta` отдаёт `reg_tg: true`): email не нужен.
  1. «Получить код в Telegram» → `POST /api/auth/tg/start`: в `tg_regs` записывается sha256 одноразового токена, сам токен — в cookie `ruwork_reg` (30 минут), браузер открывает `t.me/<бот>?start=reg_<токен>`.
  2. Бот (`support.reg_start`) запоминает чат и показывает кнопку «📱 Поделиться контактом». Если этот Telegram уже привязан к аккаунту — регистрации нет, бот предлагает войти.
  3. Контакт (`support.reg_contact`) принимается только свой (`contact.user_id == from.id`). Если номер уже зарегистрирован — кода нет. Иначе бот присылает код из 6 цифр (10 минут, 5 попыток; в базе — sha256).
  0. Сначала пользователь вводит имя и пароль и нажимает «Зарегистрироваться»: `POST /api/auth/register` с `check_only: true` только проверяет имя, пароль и согласие. Если всё верно, открывается окно «Подтвердите номер» с кнопкой «Получить код в Telegram» (шаги 1–3) и полем для кода; 6 цифр отправляются сами.
  4. Код из окна → `POST /api/auth/register` с теми же именем и паролем и `code`: код проверяется по заявке из cookie этого браузера. Аккаунт получает `users.phone` (+7XXXXXXXXXX, уникальный) и привязанный Telegram (`tg_chat`), в `users.email` — служебный адрес `…@tg.invalid`, который наружу не отдаётся (`auth.shown_email`); в списках админки вместо него показывается телефон.
- Без бота (локально) регистрация — по email: имя ≥ 2 символов и не занято, корректный email, пароль ≥ 8 символов с буквами и цифрами, совпадение паролей, согласие с условиями.
- **Удаление аккаунта** (`app/routes/delete_account.py`, блок в самом низу вкладки «Профиль»; у владельца сайта его нет). Окно сначала запрашивает `GET /api/me/delete`: что мешает (незавершённые покупки или продажи, заявки кошелька в обработке), сколько монет на балансе и привязан ли Telegram.
  - Повторное подтверждение: пароль (5 попыток за 15 минут) и, если привязан Telegram, код из 6 цифр (`POST /api/me/delete/code`: 10 минут, 5 попыток, не чаще 3 отправок за 10 минут; в базе — sha256 в `users.del_code`), плюс галочка «понимаю, что навсегда». Если на балансе есть монеты — отдельное согласие, что они сгорят: списание `adj_out`, поступление платформе `forfeit`.
  - Строка `users` не удаляется (каскад стёр бы заказы и отзывы второй стороны), а обезличивается: имя «Удалённый аккаунт <конец id>», служебная почта `deleted-…@deleted.invalid`, телефон, Telegram, фото, «О себе», роль и значок стираются, пароль — случайный, `blocked_at` и `deleted_at` выставлены (разблокировать его администратор не может). Удаляются объявления с обложками и их переписка, портфолио с файлами, избранное, подписки, сессии, адреса входа, заявки на сброс пароля и уведомления; открытые задания закрываются, отклики отзываются. Заказы, отзывы и денежные операции остаются. Тот же телефон и Telegram потом можно зарегистрировать заново.
- **Вход по коду из Telegram.** Если к аккаунту привязан Telegram (а у зарегистрированных через бота он привязан всегда), после верного пароля `POST /api/auth/login` не создаёт сессию, а возвращает `{need_code, ticket}` и отправляет код из 6 цифр в Telegram (сообщение шлёт сам сайт тем же ботом). Окно по центру экрана принимает код → `POST /api/auth/login/code` (`ticket` + `code`; 10 минут, 5 попыток, билет одноразовый, в `login_codes` — sha256 билета и кода) создаёт сессию; «Отправить код ещё раз» — `POST /api/auth/login/resend` (не чаще 3 раз за 10 минут). У сотрудника такой вход сразу подтверждает и админ-панель (`sessions.mfa_at`). Аккаунты без Telegram входят только по паролю.
- **Вход** — по телефону (в любом формате: `8 900…`, `+7 (900)…`) или email и паролю (`auth.find_user`); так же в мини-приложении и в форме сброса пароля. Старые аккаунты продолжают входить по email.
- Email нормализуется (у Gmail убираются точки и `+метки`).
- Пароль хранится как PBKDF2-SHA256, 150 000 итераций, случайная соль. Проверка идёт на сервере.
- Смена имени обновляет продавца во всех объявлениях пользователя. Смена пароля требует текущий пароль.
- **Забыл пароль** (`POST /api/auth/reset`): на странице входа пользователь указывает email, новый пароль и контакт для связи (Telegram или телефон). Новый пароль сразу хэшируется и ждёт решения администратора, сам администратор пароль не видит. Ответ одинаковый, есть такой аккаунт или нет, чтобы через форму нельзя было проверить, зарегистрирован ли email. Новая заявка заменяет прежнюю ожидающую. Пароль администратора через форму не сбрасывается.

## 6. Заказы (`app/routes/money.py`)

`POST /api/orders` с корзиной `{items:[{id,tier}], method}`. Цены берутся из БД, а не от клиента. Заказать собственную услугу нельзя: сервер отклоняет такой заказ, а на странице своего объявления и в его карточке вместо кнопок покупки показано «Это ваше объявление».

- **СБП (демо):** заказ создаётся со статусом «Ожидает подтверждения». **Сейчас временно отключена** (`SBP_ORDERS = False` в `app/logic.py`): сервер отклоняет такие заказы, а в корзине доступна только оплата с баланса. Пополнение баланса через СБП работает как прежде.
- **Баланс:** в одной транзакции проверяется и списывается баланс, пишутся операции «Оплата заказа», заказ создаётся со статусом «Ожидает подтверждения» и через минуту переходит «В работе».

```
Ожидает подтверждения ──(1 минута)──► В работе ──(24 часа)──► Выполнен
          │                               │
          └────────── Отменён ◄───────────┘
```

**Заказ и чат.** Каждый оформленный заказ добавляет в диалог покупателя по этой услуге сообщение платформы (`role = "order"`): номер, тариф, сумма и способ оплаты. Отмена заказа тоже пишет туда сообщение. После оплаты у покупателя открывается окно чата с продавцом (картинка и название товара в шапке), а в «Моих заказах» у каждого заказа есть кнопка «Чат с продавцом».

**Продавец.** У заказа хранится `seller_id` (автор объявления) и `seller_seen`. Открытая вкладка продавца раз в 10 секунд опрашивает `/api/ping`; если `new_sales > 0`, страница загружает `/api/state` (поле `sales`) и показывает окно «У вас купили товар» с картинкой, названием, номером заказа, покупателем и кнопкой «Открыть чат с покупателем». Показанное уведомление отмечается через `POST /api/sales/seen`. Все заказы по своим объявлениям видны на странице «История продаж» (`#/sales`, ссылка «Продажи» в меню): число продаж, активные, выручка без отменённых и таблица с кнопкой чата. Страница обновляется раз в 5 секунд. Заказы, пришедшие после прошлого открытия страницы, помечены «новый», а их число показано счётчиком у ссылки в меню (отметка о просмотре хранится в `localStorage` браузера).

Статусы двигает `tick()` при каждом чтении состояния; страница аккаунта опрашивает `/api/state` раз в 5 секунд. При отмене заказа, оплаченного с баланса, монеты возвращаются (операция «Возврат»): пока заказ «Ожидает подтверждения» (первая минута) — 100 % суммы, после перехода «В работе» — 90 % (`REFUND_WORK_PCT`, округление вниз). Удержанные 10 % делятся: 5 % суммы (`PLATFORM_CANCEL_PCT`) — на баланс платформы, остальное — продавцу (операция «Компенсация за отменённый заказ»). У услуг каталога RUWORK продавца нет, там всё удержание идёт платформе. Отмена заказа, оплаченного через СБП, монеты не начисляет: демо-оплата СБП ничем не проверяется.

## 6а. Результат заказа и безопасная сделка (`app/routes/orders.py`)

У каждого заказа есть страница `#/order/<id>`. Её видят покупатель, продавец и администратор (только просмотр); остальным — 404.

```
Ожидает подтверждения ──(1 мин)──► В работе ──(продавец загрузил файл)──► На проверке ──(покупатель подтвердил или прошло 7 дней)──► Выполнен
```

- **Результат.** Продавец загружает файлы (до 10 файлов, до 50 МБ каждый) в блок «Результат», пока заказ «В работе» или «На проверке». Файл передаётся частями по 512 КБ (`POST /api/orders/{id}/files`, затем `PUT …/files/{fid}?offset=N`), чтобы не упираться в лимит размера запроса на прокси. Первый полностью загруженный файл переводит заказ «На проверке» и пишет покупателю в чат. Если продавец удалит все файлы, заказ вернётся «В работе».
- **Просмотр файлов.** Картинки, видео, аудио и PDF показываются прямо на странице, остальные файлы только скачиваются (`application/octet-stream`, `nosniff`), чтобы загруженный HTML или SVG не мог выполниться на сайте.
- **Подтверждение получения.** Кнопка «Подтвердить получение» есть у покупателя, когда заказ «На проверке». Если покупатель не подтвердит, через 7 дней после перехода «На проверке» (`orders.reviewed_at`, `AUTO_CONFIRM_MS`) получение подтверждается автоматически при ближайшем обращении покупателя или продавца к сайту; срок виден на странице заказа, а в чат приходит сообщение. Заказ становится «Выполнен», и только в этот момент сумма заказа, оплаченного с баланса, зачисляется продавцу за вычетом комиссии платформы 5 % (`SALE_FEE_PCT`, округление вверх до монеты; операция «Оплата за выполненный заказ» с полем `fee`). Комиссия поступает на баланс платформы (`platform_ops.kind = "sale_fee"`). В форме объявления продавца предупреждают о комиссии, а под ценой показано, сколько он получит по каждому тарифу. До подтверждения монеты хранятся на платформе. Отменить заказ «На проверке» нельзя. За СБП-заказы продавцу монеты не начисляются: демо-оплата СБП не проверяется.
- Заказы у пользователей больше не становятся «Выполнен» через 24 часа: таймер остался только для услуг каталога RUWORK.
- **Администратор.** В списке пользователей имя открывает профиль `#/admin/user/<id>` (`GET /api/admin/users/{id}`): баланс, активные сделки как продавца, завершённые продажи, покупки и объявления. Кнопка «Результат» у сделки открывает страницу заказа в режиме просмотра.

## 6в. Спор по заказу

- **Открытие** (`POST /api/orders/{id}/dispute`, причина от 10 символов). Только покупатель, только у заказа с продавцом-пользователем в статусе «В работе» или «На проверке». Заказ получает статус «Спор» (`ST_DISPUTE`), сохраняются `dispute_at` и `dispute_reason`. Автоподтверждение через 7 дней спор не трогает, отменить заказ нельзя, оплата заморожена. Продавец может догрузить или удалить файлы результата.
- **Отзыв спора** (`POST /api/orders/{id}/dispute/close`): покупатель закрывает спор сам. Заказ возвращается «На проверке» (7 дней отсчитываются заново) или «В работе», если файлов нет.
- **Решение администратора** (`/api/admin/disputes`, вкладка «Споры»): `seller` — оплата продавцу как при обычном подтверждении (минус комиссия 5 %), `buyer` — вся сумма возвращается покупателю, заказ «Отменён», `split` — покупателю половина (с округлением вниз), продавцу остаток минус комиссия 5 % с его доли, заказ «Выполнен». Результат хранится в `dispute_result`. Монеты двигаются только за оплату с баланса. Повторное решение отклоняется.

## 6г. Уведомления и избранное (`app/routes/social.py`)

- **Колокольчик** в шапке (у вошедших): счётчик непрочитанных приходит в `/api/ping` (`notes`) и `/api/state`. Нажатие открывает список последних 50 (`GET /api/notifications`) и помечает всё прочитанным (`POST /api/notifications/read`, хранятся последние 200). Пункт ведёт по ссылке события.
- **События** (`notify()` в `app/logic.py`): продавцу — новый заказ, отмена, подтверждение получения с суммой зачисления, открытие и закрытие спора, сообщение покупателя; покупателю — загружен результат, ответ продавца, автоподтверждение, напоминание за сутки до автоподтверждения (`REMIND_MS`, один раз на заказ, поле `orders.reminded`), решение спора; обоим — решение спора; владельцу заявки — одобрение или отклонение пополнения и вывода. Сообщения чата по одной ссылке склеиваются в одно непрочитанное уведомление.
- **Избранное:** сердечко ♡ на карточке и кнопка на странице услуги (`POST /api/favs/{gig_id}` переключает). Список приходит в `/api/state` (`favs`) и показывается во вкладке кабинета «Избранное». Гостю предлагается войти.
- **Профиль продавца** (`GET /api/sellers/{id}`): без email и баланса; заблокированный пользователь — 404. «О себе» до 600 символов меняется во вкладке «Профиль» (`PATCH /api/me/about`). Имя продавца на карточке, на странице услуги и на странице заказа ведёт на профиль.

## 6б. Обложки объявлений

При размещении объявления можно выбрать обложку, а позже заменить её кнопкой «Обложка» в «Моих объявлениях». Браузер уменьшает картинку до 1280×800 и сжимает в JPEG, сервер принимает только JPG, PNG или WebP до 3 МБ (проверка по содержимому файла) и хранит её в `uploads/covers/`. Обложки отдаются по `/media/covers/<имя>`. При удалении объявления файл обложки удаляется. Без обложки показывается рисунок по подкатегории. Папка `uploads/` не хранится в git, поэтому выкладка через `rsync` её не трогает, а резервная копия базы её не включает.

**Редактирование.** Кнопка «Редактировать» в «Моих объявлениях» открывает ту же форму с заполненными полями: категория, подкатегория, название, описание, цена, теги и обложка. Сохранение идёт через `PUT /api/gigs/{id}` с теми же проверками, что и при создании (минимальная цена подкатегории и т. д.). Изменить можно только своё объявление, иначе 404. Уже оформленные заказы не меняются: у них остаются свои название и сумма. У объявления в «ТОП» можно изменить только цену: сервер сохраняет одну цену, остальные поля игнорирует, а замену обложки отклоняет (поставить первую обложку можно, если её ещё нет). В форме такие поля заблокированы, кнопка называется «Изменить цену».

## 6д. Доверие и продвижение

- **Поднятие** (`POST /api/gigs/{id}/bump`): бесплатно, раз в сутки (`BUMP_MS`). Объявление встаёт первым среди обычных: «Новые объявления» и сортировка «По популярности» при равных условиях идут по `bumped_at`.
- **Продвижение** (`POST /api/gigs/{id}/promote`): `PROMO_PRICE` = 99 монет с баланса за сутки (`PROMO_MS`), повторная покупка продлевает срок (`gigs.promo_until`). Монеты идут на баланс платформы (`platform_ops.kind = 'promo'`), у продавца — операция «Продвижение объявления». Продвигаемые объявления показываются выше всех с меткой «Продвигается». Кнопки — в «Моих объявлениях».
- **Отзывы** (`app/routes/reviews.py`, таблица `reviews`): после статуса «Выполнен» покупатель оставляет на странице заказа один отзыв (1–5 звёзд, текст, необязательное фото результата до 3 МБ в `uploads/reviews/`). Оценка сразу пересчитывает рейтинг объявления. Продавец отвечает на странице заказа или услуги (ответ можно изменить). На странице услуги фильтры «Все / С фото / Негативные» (3 звезды и ниже); отзывы из каталога RUWORK показываются после настоящих.
- **Продавец на карточке и странице:** рейтинг продавца по всем его объявлениям (`seller_ratings`), зелёная точка «в сети» (активен за 2 минуты), медианное время ответа в чате за 30 дней (`response_times`, не меньше 3 ответов, пересчёт раз в минуту), значок ✓ «Проверенный продавец» (`users.verified`, ставит администратор во вкладке «Пользователи»). В профиле продавца ещё доля сделок без споров.
- **Фильтры каталога:** «Рейтинг продавца от 4.5», «Есть отзывы», «Сейчас в сети» и сортировка «По рейтингу продавца».
- **Гарантия RUWORK:** блок у кнопки заказа, в корзине и ссылка на странице заказа ведут на `#/help` «Как проходит сделка» (ссылка есть и в подвале).
- **Похожие услуги** под страницей услуги (та же подкатегория, затем категория) и **«Вы смотрели»** на главной: до 12 последних просмотренных объявлений хранятся в браузере (`localStorage`, ключ `rw_seen`).

## 6и. Привлечение продавцов и покупателей (`app/logic.py`, `app/routes/growth.py`, `app/routes/seo.py`)

- **Комиссия 0 % в первый месяц.** `fee_pct()`: если с регистрации продавца прошло меньше `FEE_FREE_MS` (30 дней), комиссия с продажи 0 %, потом `SALE_FEE_PCT`. Так же при споре с делением пополам. В профиле продавца — карточка «Комиссия 0 %» с датой окончания (`perks.fee_free_until` в `/api/state`).
- **Реферальная программа.** У каждого аккаунта своя ссылка-приглашение `/r/<код>` (6 символов, `users.ref_code`, создаётся при первом показе; карточка «Пригласите коллег» в профиле с кнопками «Копировать ссылку» и «Поделиться» и списком приглашённых). Страница ссылки даёт превью «<имя> приглашает вас на RUWORK», ставит cookie `ruwork_ref` (id пригласившего, 30 дней) и открывает регистрацию с плашкой о бонусе. При регистрации с этого браузера новый аккаунт закрепляется за автором ссылки (`users.ref_by`), пригласившему приходит уведомление; cookie важнее `ref` из ссылок «Поделиться» (`/g/…?ref=`, запоминается в `localStorage`). Не закрепляется регистрация с адреса, с которого входил сам пригласивший. Полгода (`REF_MS`) с регистрации приглашённого `take_fee()` отдаёт пригласившему `REF_PCT` (10 %) комиссии с каждой его продажи (округление вниз) — операция `refb`, это заработок (можно вывести). В первый месяц приглашённого комиссии нет, значит и доли нет.
- **Приветственный бонус** `WELCOME_BONUS` (150) при регистрации: операция `bonus`, хранится отдельно — `wallets.bonus`, а не в монетах, поэтому его нельзя вывести или вернуть на карту. При оплате заказа с баланса бонус списывается первым (`orders.paid_bonus`), но не на заказ у связанного аккаунта (общий адрес входа в `user_ips`, `logic.linked`). Потраченный бонус — расход платформы (`platform_ops.kind = "bonus"`, минус); при отмене или споре возврат сначала идёт обратно в бонус (`refund_order`). Сверка балансов сравнивает операции с `coins + bonus`. При удалении аккаунта бонус сгорает.
- **Опыт на других площадках.** Продавец присылает ссылку на профиль (`POST /api/me/ext`; только площадки из `EXT_SITES`: Kwork, FL.ru, Профи.ру, YouDo, Хабр Фриланс и др.), рейтинг и число отзывов. Чтобы подтвердить, что профиль его, он добавляет в описание там ссылку на свой профиль RUWORK. Администратор проверяет во вкладке «Площадки» и одобряет (значок «Проверенный продавец», в публичном профиле — «Опыт на …» с рейтингом и ссылкой) или отклоняет с причиной.
- **«Поделиться» с бонусом.** Ссылка продавца на своё объявление `/g/<id>?ref=<id продавца>`. Страница при открытии отправляет `POST /api/share/visit`; считается один переход на адрес (хэш), свои заходы (аккаунт продавца и адреса, с которых он входил) не считаются. На `SHARE_VISITS` (5) переходов объявление бесплатно продвигается сутки (`gigs.share_reward_at`), не чаще раза в 30 дней. Прогресс — под объявлением в «Моих объявлениях» (`GET /api/me/share`).
- **Биржа заданий как вход.** На главной под поиском — «Опишите задачу — продавцы сами предложат цену»; SEO-страницы ведут на `/?req=1#/requests`, что сразу открывает форму задания.
- **SEO-страницы.** Сервер собирает обычный HTML: `/uslugi` (все категории), `/uslugi/<категория>`, `/uslugi/<категория>/<подкатегория-транслитом>` — заголовок и описание с минимальной ценой, до 60 объявлений, соседние подкатегории, призывы разместить задание и стать продавцом. `/sitemap.xml` и `/robots.txt`. Ссылка «Все услуги» — в подвале сайта.

## 6ж. Срок, правки и продление (`app/routes/orders.py`)

- В заказе хранятся срок `days` и число правок `revs`: из тарифа на момент покупки или из отклика на бирже. Срок сдачи `deadline()` = `started_at` + (`days` + `extra_days`) дней. Первая загрузка результата пишет `delivered_at`; по нему считается «сдано в срок» (в заказе, у продавца и в уровне).
- **Доработка** (`POST /api/orders/{id}/revision`): покупатель, заказ «На проверке», есть неиспользованные правки (`revs_used < revs`). Заказ снова «В работе», автоподтверждение останавливается до новой загрузки.
- **Продление** (`POST /api/orders/{id}/extend`, 1–7 дней с причиной): продавец, заказ «В работе», один открытый запрос (`ext_days`, `ext_reason`). Покупатель отвечает `…/extend/accept` (дни добавляются в `extra_days`) или `…/extend/decline`.
- На странице заказа: этапы с датами, таймер до срока (оранжевый меньше чем за сутки, красный после просрочки, обновляется раз в 30 с), счётчик правок, блок запроса продления.

## 6з. Биржа, уровни, статистика, подписки, портфолио, отпуск (`app/routes/market.py`)

- **Биржа заданий** (`#/requests`, `#/request/<id>`): покупатель публикует задание (`requests`: категория, бюджет, срок; не больше 5 открытых). Продавец откликается одним из своих объявлений с ценой, сроком и текстом (`offers`, один отклик на задание, повторный заменяет прежний). Автор видит все отклики, продавец — свой. «Выбрать и оплатить» (`POST /api/offers/{id}/accept`) списывает цену с баланса и через `place_order()` создаёт обычный заказ по объявлению продавца («Заказ с биржи», срок из отклика); задание становится «Исполнитель выбран», остальные отклики — отклонены.
- **Уровни продавца** (`LEVELS`, `seller_level()` в `app/logic.py`): Новичок → Уровень 1 → Уровень 2 → Профи по выполненным заказам, отзывам, рейтингу, доле сданных в срок, доле споров и времени ответа. Показатели считаются раз в минуту. Уровень виден в карточках, на странице услуги, в профиле и в откликах; во вкладке «Статистика» — условия следующего уровня.
- **Статистика** (`GET /api/me/stats`, вкладка кабинета): по каждому объявлению просмотры (всего и за 30 дней), избранное, сколько написали в чат, заказы, конверсия и выручка. Просмотр (`POST /api/gigs/{id}/view`, таблица `gig_views`) считается раз в сутки на посетителя, свои не считаются.
- **Подписки на поиск** (`saved_searches`, до 10): кнопка «Сообщать о новых» в каталоге сохраняет запрос, категорию, подкатегорию и цену. Новое объявление (`create_gig` → `notify_searches`) уведомляет подходящих подписчиков на сайте и в Telegram. Список подписок — во вкладке «Избранное».
- **Портфолио** (`portfolio`, до 30 картинок, `/media/portfolio/…`): загружается в профиле кабинета, можно привязать к объявлению. Показывается в профиле продавца и в галерее объявления (привязанные — первыми).
- **Режим «В отпуске»** (`users.vacation_until`, до 90 дней): объявления остаются в каталоге с датой возвращения, но заказ и отклик на бирже сервер отклоняет. Текущие заказы не затрагиваются.

## 6е. Телефон и установка как приложение

На телефоне (класс `phone`): окна открываются шторкой снизу и закрываются свайпом вниз; фильтры каталога — кнопкой «Фильтры · N» внизу и шторкой на весь экран с кнопкой «Показать N услуг»; чат на странице услуги открывается кнопкой «Написать продавцу»; поля ввода 16 px (iPhone не увеличивает страницу); вкладки кабинета прилипают под шапкой; таблицы заказов и операций показываются карточками; обложка услуги во всю ширину, под ней фото из отзывов; в кабинете и на странице заказа данные обновляются жестом «потянуть вниз». Кнопка «↑ Наверх» появляется после прокрутки на любом устройстве.

`public/manifest.json`, иконки `icon-192.png`/`icon-512.png` и `sw.js` позволяют добавить сайт на главный экран: он открывается без адресной строки. Сервис-воркер ничего не кэширует, поэтому выкладка обновляет сайт сразу.

- **Нижняя панель:** Главная, Каталог, Корзина, Биржа, Кабинет; счётчик непрочитанных уведомлений — на «Кабинете» (сами уведомления — кнопкой в кабинете).
- **Заказ:** в шапке «Чат» и меню «⋯» (`ordMore`: отмена, объявление, мои заказы/продажи, помощь). Главное действие закреплено над нижней панелью (`ordBar`): покупателю на проверке — «Подтвердить получение» и «Доработка», продавцу — «Загрузить результат», покупателю при запросе продления — ответ на него.
- **Корзина:** итог и «Оплатить» закреплены внизу, оплата с баланса — в шторке (`paySheet`).
- **Чат** открывается на весь экран; окно подстраивается под клавиатуру через `visualViewport` (`vvFit`), поле ввода всегда над ней. Продавцу над полем — быстрые ответы (`QREP`), отправляются одним нажатием.
- Класс `phone` и тема ставятся скриптами в `<head>` до первой отрисовки. Шапка, нижняя панель и окна не разваливаются при крупном шрифте в настройках телефона.
## 7. Кошелёк

- **Две части баланса.** `wallets.coins` — весь баланс, `wallets.earned` — заработок (оплата за продажи, компенсации за отменённые заказы, доля продавца в споре). Разница — **аванс**: пополненные монеты. Аванс нельзя вывести на другие реквизиты, только потратить или вернуть на исходный платёж; так нет схемы «пополнил и вывел», которую платёжные системы считают транзитной (115-ФЗ). Оплата заказов и продвижения (`spend()`) берёт сначала аванс, потом заработок; сколько заказа оплачено из аванса, хранится в `orders.paid_adv`. Возврат за отмену или спор (`refund_back()`) кладёт в аванс не больше `paid_adv`, остальное — в заработок. При первом запуске заработок старых балансов = продажи и компенсации минус выводы, не больше баланса.
- **Пополнение:** целое число 100–100 000 → заявка «В обработке». Монеты зачисляются в аванс после одобрения администратором.
- **Возврат на карту** (`POST /api/wallet/refund`, `t = 'rf'`): не больше аванса. Сумма раскладывается по одобренным пополнениям, начиная с последних, — по заявке на каждый платёж (`wallet_ops.src`), не больше ещё не возвращённой части этого платежа. Монеты удерживаются при создании заявки. В реальном запуске одобрение — это возврат платежа через API шлюза.
- **Вывод:** только заработок, от 500 монет, телефон `+7XXXXXXXXXX`, банк из списка, подтверждение паролем на сервере. Комиссия 2 %, минимум 10 монет. Монеты удерживаются при создании заявки. Администратор подтверждает выплату или отклоняет заявку, и тогда монеты возвращаются.
- Пользователь может только отменить свою ожидающую заявку. Подтвердить её сам он не может.

## 8. Свои объявления

Категория, подкатегория, название, описание, цена (≥ 100 ₽ и не ниже минимума подкатегории), до 5 тегов. Текст экранируется на сервере. Удалить можно только своё объявление.

## 9. Администрирование (`app/routes/admin.py`, `app/routes/admin_tools.py`)

**Доступ и роли.** Владелец — аккаунт `ADMIN_EMAIL = phantom.crypta@mail.ru` с именем `ruwork.shop`, создаётся при старте (`ensure_admin`), если задан `RUWORK_ADMIN_PASSWORD`. Владелец может выдать роль «модератор» (`users.role = 'moder'`, кнопка в профиле пользователя). `public_user` отдаёт `staff: "admin" | "moder"`, по нему фронтенд показывает ссылку «Админ».
- `auth.require_staff` — любой сотрудник с подтверждённым вторым фактором; `auth.require_admin` — только владелец. Модератору доступны сводка (без денежных пунктов), споры, жалобы, объявления, пользователи (блокировка, значок, сообщения), чаты, поиск. Деньги, заявки, сброс паролей, баланс платформы, сверка, корректировка, графики, журнал, настройки и роли — только владельцу. Модератор не может действовать над другими сотрудниками.
- **Второй фактор** (`/api/staff/mfa`, `send`, `verify`): если настроен бот (`RUWORK_TG_TOKEN`) и не задано `RUWORK_ADMIN_2FA=0`, любой запрос к `/api/admin/*` без подтверждения в этой сессии получает 428. Код из 6 цифр приходит в Telegram сотрудника, живёт 10 минут, 5 попыток, не чаще 3 отправок за 10 минут; подтверждение действует 12 часов (`sessions.mfa_at`). Вход пишется в журнал, владельцу приходит оповещение. Telegram сотрудника нельзя отвязать или перепривязать с сайта и через мини-приложение — иначе укравший пароль привязал бы свой; первую привязку сделать можно, сменить — только в базе.

**Вкладки** (`#/admin/<вкладка>`): «Сводка» (по умолчанию), «Деньги», «Споры», «Жалобы», «Объявления», «Пользователи», «Чаты», «Сброс пароля», «Онлайн», «Журнал»; профиль — `#/admin/user/<id>`. Над вкладками — глобальный поиск. Панель обновляется раз в 5 секунд.
- **Сводка** (`/api/admin/attention`): что требует действия — заявки старше суток и новые, выводы на проверке, сброс паролей, открытые споры (с возрастом самого старого), жалобы, объявления на проверке, просроченные заказы, ошибки 500 за сутки (таблица `errors`, хранится 30 дней), сбой бэкапа, расхождения балансов. Каждая строка ведёт к нужной вкладке. Тут же переключатель премодерации и графики.
- **Графики** (`/api/admin/stats?days=7|30|90`, по московским дням): оборот (заказы без отменённых), доход платформы, заказы, регистрации, новые объявления — по графику на величину; воронки продавца (регистрация → объявление → первый заказ → завершённая продажа) и покупателя; таблица по дням.
- **Деньги**: баланс платформы; **сверка** (`/api/admin/reconcile`) пересчитывает баланс каждого кошелька по `wallet_ops` (`LEDGER_SQL`: пополнения, возвраты, продажи, компенсации и начисления — плюс; оплаты, продвижение и списания — минус; выводы и возвраты на карту — минус, пока заявка ожидает или выполнена) и показывает расхождения; заявки с полным телефоном вывода (`wallet_ops.phone`) и **флагами риска** (`wd_flags`): аккаунт моложе 7 дней, первый вывод, сумма больше обычной в 3 раза, все продажи (от двух) одному покупателю, покупатель заходил с адреса продавца, телефон указывал другой аккаунт. Одобрение заявки с флагами просит подтверждения.
- **Корректировка баланса** (`POST /api/admin/users/{id}/adjust`, профиль пользователя): плюс — начислить, минус — списать, в заработок или аванс, с обязательной причиной. Операция `adj_in` / `adj_out` видна пользователю в кошельке, ему приходит уведомление; списать больше выбранной части баланса нельзя.
- **Заявки** одобряются и отклоняются как раньше: одобрение пополнения зачисляет монеты, отклонение вывода или возврата возвращает удержанное.
- **Объявления**: фильтр «Все / На проверке / Скрытые». **Премодерация** (настройка `premod` в таблице `settings`): первые `PREMOD_FIRST = 3` объявления непроверенного продавца создаются с `gigs.mod = 'pending'`. «Опубликовать» ставит `ok` и рассылает подписки на поиск, «Скрыть» — `hidden` с причиной (`mod_note`): автор видит её в кабинете, а после исправления объявление снова уходит на проверку. Не `ok` объявления видит только автор (`/api/gigs` отдаёт ему их с `mod`), их нельзя заказать и откликнуться ими. «Удалить» — навсегда.
- **Пользователи и профиль**: блокировка с причиной на 1, 7, 30 дней или бессрочно (`users.blocked_until`; фоновая задача снимает её по сроку, при входе пользователь видит дату), значок «Проверенный продавец», роль, сообщение от администрации (с шаблонами; приходит в колокольчик и Telegram), баланс по частям, корректировка, **связанные аккаунты** (общий адрес входа — кроме адресов, с которых заходят больше 10 человек, — или общий телефон вывода), адреса входа (`user_ips`: пишутся при регистрации, входе и раз в 30 секунд активности) и журнал действий по пользователю.
- **Споры**: «Подробнее» открывает карточку (`/api/admin/dispute/{id}`): обе стороны с числом заказов и прошлых споров, рейтинг продавца, предупреждение, если стороны связаны, ход заказа (оформлен, в работе, срок, сдан — с пометкой об опоздании, продления, правки), файлы результата и вся переписка. Решение — как раньше: продавцу, покупателю или пополам.
- **Жалобы**: «Написать автору», «Скрыть объявление», «Удалить», «Заблокировать автора», «Разобрана».
- **Чаты** (`/api/admin/chats`, `/chats/thread`): поиск по переписке покупателей и продавцов, фильтр «Только со скрытыми контактами», список тех, кто чаще всех пытался обменяться контактами за 30 дней, просмотр диалога целиком. О том, что администрация может читать переписку для разбора жалоб и споров, стоит написать в политике конфиденциальности.
- **Массовые действия**: галочки в заявках, объявлениях и жалобах и панель «Одобрить / Отклонить / Опубликовать / Скрыть / Удалить / Отметить разобранными» — выполняется по одному запросу на объект, каждый пишется в журнал.
- **Журнал** (`admin_log`, `/api/admin/log`): кто, когда, что сделал, с каким пользователем и на какую сумму — решения по заявкам, сбросу паролей и спорам, блокировки, значки, модерация объявлений, жалобы, корректировки, сообщения, настройки, роли и входы в панель.
- **Сброс пароля** и **Онлайн** — без изменений: администратор связывается с владельцем по контакту из заявки; онлайн — активные за 2 минуты (`ONLINE_MS`).

## 10. Чат с продавцом (`app/routes/chat.py`)

**Объявления пользователей — живой диалог покупателя с продавцом.**
- Написать продавцу может только вошедший пользователь. Сообщение сохраняется с `owner = "u:<id покупателя>"`, `role = "me"`, ИИ не отвечает.
- Продавец на странице своего объявления видит блок «Сообщения покупателей»: отдельный диалог с каждым покупателем (свежие сверху, с пометкой «ждёт ответа») и поле ответа. Ответ (`POST /api/chat/{id}/reply`) сохраняется в тот же диалог с `role = "seller"`.
- В «Мои объявления» у объявления видно «ждут ответа: N» — число диалогов, где последнее сообщение от покупателя или о новом заказе (`inbox` в `/api/state`).
- Обе стороны получают новые сообщения без перезагрузки: страница объявления опрашивает чат раз в 5 секунд. Чужие диалоги не видны никому, кроме продавца.

**Встроенный каталог RUWORK — ИИ-ответчик.**

- Сообщение сохраняется в БД, затем сервер формирует ответ.
- Если задан `ANTHROPIC_API_KEY`, ответ пишет Claude по данным услуги и последним 10 сообщениям (до 600 символов, без подтверждения заказов и выдуманных цен).
- Без ключа, при ошибке API или отказе модели отвечает `local_reply()` по ключевым словам: цена, сроки, правки, оплата, приветствие.

## 10а. Поддержка в Telegram-боте (`app/support.py`)

Тот же бот, что шлёт уведомления. Клиенту на `/start`, `/menu` показывается меню частых вопросов (кнопки → готовые ответы из словаря `FAQ`) и «Написать оператору». Любое другое сообщение клиента бот пересылает в чат поддержки (`RUWORK_TG_SUPPORT_CHAT`: личный чат оператора или группа) с шапкой: имя, @username, chat_id и аккаунт RUWORK, если чат привязан к уведомлениям. Клиент получает «Сообщение передано оператору» (не чаще раза в 10 минут).

Оператор отвечает реплаем на шапку или сообщение клиента — текст, фото или файл уходит клиенту от имени бота, на ответе появляется 👍. Реплай `/t <ключ>` отправляет шаблон; `/t` без реплая показывает список ключей (в т. ч. служебные: `hello`, `num`, `check`, `block`, `bye`). Команда `/id` в любом чате показывает его chat_id. Без `RUWORK_TG_SUPPORT_CHAT` бот отвечает только меню и направляет к @ruwork001.

## 10б. Защита, модерация и обслуживание (`app/guard.py`, `app/jobs.py`, `app/routes/reports.py`)

- **Демо-каталог выключен** (`DEMO_CATALOG = False` в `app/logic.py`): встроенные услуги `g-…` остаются в базе, но не попадают в `/api/gigs`, их нельзя заказать, открыть в чате или в `/g/<id>`, а `/api/meta` не отдаёт их продавцов. Пустой каталог на главной показывает призыв «Станьте одним из первых продавцов».
- **Ограничение частоты** (в памяти процесса, `guard.limited/hit/throttle`): вход — 20 неудачных попыток с адреса и 10 в один аккаунт за 15 минут (ключ по email общий с мини-приложением), регистрация — 5 в час с адреса, сброс пароля — 5 в час с адреса и 3 на email, чат — 30 сообщений в минуту, жалобы — 10 в час. Адрес берётся из `X-Real-IP` / `X-Forwarded-For` (nginx), иначе из соединения. Для несуществующего email считается такой же хэш, чтобы время ответа не выдавало аккаунт.
- **Сброс пароля через Telegram:** если к аккаунту привязан Telegram, бот присылает кнопку «Да, сменить пароль» (`GET /api/auth/reset/tg/<токен>`, 30 минут, в базе хранится sha256 токена). Нажатие ставит новый пароль и завершает все сессии. Без Telegram заявку по-прежнему одобряет администратор, ему приходит оповещение.
- **Контакты в переписке** (`guard.mask_contacts`): в чате с продавцом (сайт и мини-приложение), в описании и названии объявлений, заданий, откликов и в «О себе» телефоны, email, @юзернеймы и ссылки заменяются на «[контакт скрыт]». Ссылки на ruwork.shop остаются.
- **Запрещённые услуги** (`guard.check_banned`, список `BANNED`): объявление или задание с такими словами отклоняется с ошибкой 400.
- **Жалобы** (`reports`): кнопка «Пожаловаться» на странице объявления, в профиле продавца и в задании биржи. Причина из списка `REASONS` (приходит в `/api/meta` как `report_reasons`), повторная жалоба того же пользователя обновляет прежнюю. Администратор разбирает их во вкладке «Жалобы»: ссылка на объект, «Удалить объявление», «Заблокировать автора», «Разобрана» (закрывает все жалобы на этот объект).
- **Оповещения администратору в Telegram** (`guard.alert`): заявки на пополнение и вывод, сброс пароля без Telegram, новый спор, жалоба, ошибка 500 (одна на адрес раз в 10 минут), сбой резервной копии. Чат: `RUWORK_TG_ADMIN_CHAT`, иначе Telegram, привязанный к аккаунту администратора, иначе чат поддержки.
- **Фоновые задачи** (`app/jobs.py`, поток в одном процессе — блокировка `.jobs.lock`): раз в минуту `tick()` для всех с активными заказами (автоподтверждение и напоминания работают без захода на сайт) и напоминания о сроке (`orders.dl_reminded`): продавцу — за сутки до срока, обоим — когда срок прошёл; принятое продление начинает напоминания заново. Раз в сутки — копия базы через SQLite backup API в `backups/ruwork-ГГГГММДД-ЧЧММ.db.gz`, хранятся 14 последних; с `RUWORK_TG_BACKUP_CHAT` копия ещё отправляется в этот Telegram-чат.
- **`/api/health`**: 200 `{"ok": true}`, если база отвечает, фоновые задачи шли последние 10 минут и последний бэкап удался; иначе 503 со списком проблем. Для UptimeRobot и т. п.
- **Онбординг продавца:** во вкладке «Объявления» карточка «Старт продавца» (фото, «О себе», Telegram, первое объявление) — пропадает, когда всё сделано. В форме объявления — подсказки и индикатор «Качество объявления» (название от 20 символов, описание от 300, обложка, 3+ тега, цена); публиковать можно и без них. Описание — до 1000 символов. Пользователям без Telegram в кабинете показывается плашка «Подключите Telegram».
- **Сквозной прогон** `scripts/e2e.py`: поднимает сервер на временной базе и проходит путь покупателя, продавца и администратора через API (30 проверок).

## 11. Ограничения демо

- Платежи и выводы не настоящие: администратор подтверждает их вручную. Для реального запуска поступление денег должен подтверждать платёжный шлюз.
- Сессии хранятся в SQLite; для нескольких серверов понадобится общая БД (например, PostgreSQL).
